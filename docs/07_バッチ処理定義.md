# バッチ処理定義：電車ルート検索アプリ

作成日：2026-11-18／対応文書：docs/01_基本設計書.md、docs/04_詳細設計書.md

## 1. 結論

定常バッチ処理（定期実行ジョブ）は定義しない。理由は次のとおり。

- 永続データは利用者のブラウザ内（localStorage）に閉じており、サーバー側で定期的に処理すべきデータが存在しない。
- 唯一の定期性のある処理「月間カウンターの月次リセット」は、読み取り時の遅延評価で代替でき、バッチ化する利点がない。
- サーバー側キャッシュは TTL 60 秒で自動失効し、掃除ジョブが不要である。

## 2. バッチ相当の処理（代替手段の定義）

バッチの代わりに、次の処理を通常リクエスト処理の中で実行するものとして定義する。

| # | 処理名 | 本来のバッチ相当の役割 | 代替手段 | 実行タイミング | 実装 |
|---|---|---|---|---|---|
| BT-01 | 月次リセット | 月替わりでカウンターを 0 に戻す | 遅延評価：読み取り時に保存月と現在月を比較し、異なれば 0 件として扱う | 画面表示時・検索前（OP-01） | usage.loadUsage／increment |
| BT-02 | キャッシュ失効 | 古いキャッシュの削除 | TTL 方式：取得時に失効していたら削除して未ヒットとして扱う | キャッシュ取得時（OP-10） | cache.get |
| BT-03 | 履歴の押し出し | 履歴の件数整理 | 登録時に最大 10 件を超えた分を末尾から削除する | 検索成功時（OP-05） | page.tsx |

## 3. バッチが必要になる条件

次のいずれかを導入する場合は、本書を改訂しバッチ処理を正式に定義すること。

- サーバー側に永続データを置く（RDB 導入、アカウント機能など）
- 利用状況の集計・レポートを定期的に作る
- 外部 API の利用量をサーバー側で締め処理する
