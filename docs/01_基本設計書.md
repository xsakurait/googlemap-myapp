# 基本設計書：電車ルート検索アプリ（Next.js）

作成日：2026-11-17／対応要件：docs/00_要件定義書.md

## 1. システム概要

目的地を入力すると、デフォルトで現在時刻を基準に「次の便」から検索し、最安・最短・乗り換え最少を総合したおすすめルートを先頭に表示する個人用Webアプリ。出発地のデフォルトは現在地GPS（座標を緯度経度のまま Google Routes API に渡す）。使用APIは Google Routes API（Compute Routes、TRANSIT）のみで、無料枠（Essentials SKU：月10,000件）の範囲内で使うことを最優先の制約とする。DBは持たず、保存はブラウザの localStorage のみ。主にユーザーのPCブラウザ（localhost:3000）で使う。

## 2. システム構成

| 層 | 技術 | 役割 |
|---|---|---|
| ブラウザ（クライアント） | Next.js App Router の Client Component（`src/app/page.tsx`） | 入力、GPS取得、結果表示、履歴・カウンターの localStorage 保存 |
| サーバー | Next.js Route Handler（`src/app/api/routes/route.ts`） | APIキーを保持し、検証・キャッシュ・Routes API 呼び出し・正規化を行う |
| 外部 | Google Routes API `computeRoutes` | 電車ルート・時刻・運賃（推定）の提供 |

```
[ブラウザ]
  ├─ Geolocation API → 緯度経度
  ├─ localStorage（履歴 / 月間カウンター / 設定 / 前回出発地）
  └─ POST /api/routes { origin, destination, offsetMinutes, mock? }
        │
[Next.js サーバー（ユーザーのPC, localhost:3000）]
  ├─ 入力バリデーション（lib/google-client.parseSearchParams）
  ├─ サーバー側メモリキャッシュ（同一条件60秒、lib/cache）
  └─ POST https://routes.googleapis.com/directions/v2:computeRoutes
        ヘッダー: X-Goog-Api-Key（環境変数 GOOGLE_MAPS_API_KEY）, X-Goog-FieldMask
        │
[Google Routes API] → 応答JSON → 正規化（lib/routes-normalize）→ ブラウザへ
```

ブラウザは Routes API を直接呼ばない（キーをブラウザに出さないため）。並び替え・バッジ付けは候補が最大4件しかないためブラウザ側（lib/ranking）で実施し、並び替え変更でAPIを再消費しない。

## 3. 処理フロー

1. 画面表示時に Geolocation で現在地を取得する（拒否・失敗時は手入力へフォールバックし、その旨を表示）。
2. ユーザーが目的地を入力して検索。クライアントは月間カウンターの停止判定を先に行い、停止中なら検索しない。
3. サーバーは入力を検証し、`departureTime = 現在時刻（Asia/Tokyo基準の実時刻）+ offsetMinutes` を RFC3339 UTC で組み立てて Routes API を1回だけ呼ぶ（代替ルートは `computeAlternativeRoutes: true` で同一リクエスト内取得）。
4. 応答を NormalizedRoute[] に正規化して返す。同一条件の再検索はサーバー側キャッシュ（60秒）から返し、`cached: true` を付ける。
5. ブラウザは選択中のモードで並び替えて表示。実API・非キャッシュ応答のときだけ月間カウンターを+1する。検索条件を履歴（最大10件）へ保存する。
6. モックモード時はサーバーがフィクスチャ（lib/mock-data）を正規化して返し（`source: "mock"`）、カウンター対象外とする。

## 4. 共通処理

### 4.1 現在時刻・出発時刻計算（lib/time.computeDepartureIso）

- 基準はサーバー／ブラウザの現在時刻。`new Date(now + offsetMinutes分).toISOString()` で RFC3339 UTC 文字列化する。
- offsetMinutes は 0〜180 の整数（検証は lib/google-client）。表示時刻は Asia/Tokyo 固定で `HH:mm` 整形（lib/time.formatHm）。

### 4.2 月間カウンターと月次リセット（lib/usage）

- 状態は `{ month: "YYYY-MM"（Asia/Tokyo）, count }` を localStorage に保存。
- 月次リセットは「読取時の遅延リセット」：`loadUsage` が保存値の month と現在月を比べ、違えば 0件として返す。加算時（`increment`）も月が違えば新月の1件目にする。定期実行は不要（§5）。
- 判定は `checkLimit`：count >= stopAt → `stop`（検索不可）、>= warnAt → `warn`（警告表示）。初期値 warnAt=8000 / stopAt=10000、画面の設定から変更可（localStorage 保存）。
- 加算タイミング：実API応答かつ非キャッシュのときだけ。モック・キャッシュ・エラー時は加算しない。

### 4.3 キャッシュ（lib/cache）

- サーバー側プロセス内メモリの TTL 付き Map。TTL 60秒、キーは検索条件の安定文字列化（キー順非依存）。
- 期限切れエントリは取得時に破棄する（掃除バッチなし）。プロセス再起動で全消去されるが、用途上問題ない。
- クライアント側キャッシュは持たない。

### 4.4 エラーコード体系と表示変換

内部エラーコードは5種（詳細は 05_API設計書 §4）。サーバーは `{ error: { code, message } }` とHTTPステータスを返し、ブラウザはコードごとに固定文言へ変換して表示する（APIキー未設定時はセットアップ手順への案内を併記）。上流の生エラー文はそのまま表示しない。

### 4.5 入力バリデーション（lib/google-client.parseSearchParams）

- destination：必須、空白のみは不可（trim後に判定）。
- origin：latLng（緯度 -90〜90、経度 -180〜180 の数値）か address（空でない文字列）のどちらか必須。
- offsetMinutes：省略時0、0〜180の整数以外は 400。
- 不正はすべて `INVALID_PARAMS`（HTTP 400）として早期に返す（APIを消費しない）。

### 4.6 ログ方針

- サーバー：Next.js の標準出力のみ。APIキー、緯度経度の生値はログに出さない。
- ブラウザ：localStorage に検索履歴（目的地・出発地ラベル等）を保存するが、これはユーザー本人のPC内のみ。
- 監視・アラートは個人利用のため設けない。利用量の把握は月間カウンター表示と Google Cloud コンソールのクォータ画面で行う。

## 5. バッチ処理の要否判断

**結論：バッチ処理は作らない。**

| 候補だった処理 | バッチにしない理由（代替手段） |
|---|---|
| 月間カウンターの月次リセット | サーバーに永続データがなく、カウンターはブラウザの localStorage 内。読取・加算のたびに月を比較する遅延評価で完全に代替できる |
| キャッシュの期限切れ掃除 | TTL 60秒の小規模メモリキャッシュであり、取得時に期限切れを破棄すれば十分。残存してもプロセス再起動で消える |
| 無料枠の集計・レポート | 個人利用で集計対象が単一ブラウザのみ。画面カウンターと Cloud コンソールのクォータで足りる |

将来バッチが必要になる条件：

- 複数端末・複数ブラウザで利用量を合算したくなった場合（カウンターのサーバー集約＋定期集計が必要になる）。
- 検索履歴をサーバー側DBに保存し、古い履歴の定期削除が必要になった場合。
- 定期的な運行情報チェックなど、ユーザー操作なしに動く機能を追加した場合。

## 6. 無料枠ガード設計

多層で守る：

1. 検索1回 = API 1リクエスト（代替ルートは同一リクエスト内）。並び替え変更・GPS取得ではAPIを呼ばない。
2. サーバー側60秒キャッシュで同一条件の連打を吸収。
3. ブラウザ側月間カウンター：8,000件で警告、10,000件で自動停止（変更可）。
4. Google Cloud 側のクォータ上限設定を推奨（手順は 06_セットアップ手順）。アプリ側カウンターは localStorage のため、ブラウザを変えると数え直しになる点が限界であり、最終防衛線は Cloud 側に置く。

SKU の根拠：本アプリのリクエストは Pro トリガー（中間地点11〜25個・optimizeWaypointOrder・TRAFFIC_AWARE系・location modifiers）にも Enterprise トリガー（二輪・通行料計算等）にも該当しないため、transitDetails / transitFare を含むフィールドマスクでも Essentials SKU（無料枠 月10,000件）になる（2026-11-17 Google公式SKU詳細で確認。詳細は 05_API設計書 §5）。

## 7. セキュリティ（キー管理）

- APIキーはサーバー側環境変数 `GOOGLE_MAPS_API_KEY`（`.env.local`）のみ。コード・ZIP・チャットに含めない。`.env.local` は `.gitignore` 対象。
- Google Cloud 側でキーに API 制限（Routes API のみ）を付ける手順を同梱（06_セットアップ手順）。
- 内部APIは localhost 前提で認証を設けない（個人PC内利用のみがスコープ。公開する場合は認証追加が必須であり v1 スコープ外）。
- 位置情報は検索のたびにブラウザ許可のもとで取得し、サーバーへは検索条件としてのみ送る。サーバー側に保存しない。
