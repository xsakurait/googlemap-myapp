# コーディング規約と CI チェック

製造コードの規約と、それを CI でどう判定するかを定める。チェックの実体は `scripts/check-conventions.mjs`（依存なし・Node 標準のみ）で、CI（`.github/workflows/ci.yml`）の「Convention check」ステップで毎回実行する。違反があれば CI が失敗する。

## 1. 構成

- 配置を許可するルートは `src/app`（画面・API）、`src/lib`（共通）、`src/features`（機能単位）の 3 つとし、それ以外の場所へのコード配置を違反とする。
- 構成の判定結果はチェック実行時に出力する。`src/features` 配下に機能単位のコードがあれば feature ベース、なければレイヤー型と判定する。
- 現状の判定（2026-11-18）：レイヤー型（`src/lib` 集約）であり、feature ベースではない。バス・飛行機の拡張など機能追加の際は `src/features` へ配置し、段階的に feature ベースへ移行する。

## 2. 命名規則

基本的な規則に統一し、CI で機械的に判定する。

| 対象 | 規則 | 例 |
| --- | --- | --- |
| ファイル名 | kebab-case | `routes-normalize.ts` |
| クラス・型・インターフェース | PascalCase | `NormalizedRoute` |
| 関数・変数 | camelCase | `scoreRoutes` |
| 定数 | camelCase / PascalCase / UPPER_SNAKE_CASE のいずれか | `WEIGHTS` |

Next.js のルートハンドラ（GET／POST 等）は例外として許可する。

## 3. コメントの規約

- コメントに個人名・AI 名を書かない。対象はチェックスクリプト内の禁止語リスト（個人名、Muse／ChatGPT／Copilot／Gemini 等の AI 名、「AI生成」の類）で、コメント行に含まれていれば違反とする。
- export する関数・クラスには、直前にコメント（1 行でよい）を付ける。処理の都度、メソッド単位で付けること。

## 4. CI での判定

- 実行タイミング：push と pull_request（CI ワークフローの一部）。
- 判定方法：`node scripts/check-conventions.mjs` が `src` 配下を走査し、構成・命名・コメント禁止語・メソッドコメントの 4 観点を検査する。違反は一覧で出力され、1 件でもあれば CI 失敗となる。
- 構成の判定（feature ベースか）は合否ではなく結果として出力する。合否に含めるかは、移行方針が決まった時点で見直す。
